# スクリーンショット付きドキュメント記事

## ワークフロー

1. 執筆前に、対象の docs ディレクトリ、既存の README、スクリーンショット、ルート README、パッケージマニフェスト、関連するソースファイルを確認する。
2. 可能な範囲で、ローカルファイルとコマンドから実際のワークフローを確認する。セットアップやテストのドキュメントでは、低コストかつ安全に実行できるローカルコマンドを実行し、その実結果を反映する。
3. 依頼にスクリーンショットが含まれる場合は、順番に確認する。記事の各セクションを UI の手順、ボタンラベル、プロンプト、成功状態に対応付ける。
4. 執筆前に安定したドキュメント用スラッグを決める。長すぎる名前やスペルミスのある名前ではなく、`setup-codex-claude-environment` のように短く、正しい綴りで、操作が分かる名前を優先する。
5. 記事が拡張される可能性がある場合や、ユーザーが拡張しやすい構成を求めている場合は、スクリーンショットを `images/` 配下に整理する。リンクは `./images/1.png` のように README からの相対パスにする。
6. 記事は逐語的な記録ではなく、実用的なガイドとして書く。必要に応じて、前提条件、対象リポジトリやコンテキスト、番号付き手順、コマンド、期待される出力、注意点、短いまとめを含める。
7. 編集後に最終的なツリーと Markdown の参照を検証する。古いパス、壊れた画像リンク、誤字のあるディレクトリ名、リポジトリのスクリプトと異なるコマンドがないか確認する。

## Markdown スタイル

- リポジトリの言語とトーンに合わせる。リポジトリや AGENTS の指示で日本語が指定されている場合は、簡潔で丁寧な日本語で書く。
- スクリーンショットの流れに合う明確な見出しを使う。
- コマンドは適切な情報文字列付きの fenced code block に入れる。
- 画像の alt テキストは意味があり、短いものにする。
- 注意点は、実際に対処可能なもの、またはログに出る無害なノイズを説明するものに限って記載する。
- 明らかな UI 操作を説明しすぎない。読者が何を選択し、何を確認すべきかに集中する。

## ディレクトリ規約

スクリーンショットが多い記事では、次の構成を使う。

```text
docs/<article-slug>/
├── README.md
└── images/
    ├── 1.png
    ├── 2.png
    └── ...
```

スクリーンショットがすでに `1.png`、`2.png` などの名前になっている場合、ユーザーが説明的な名前を求めない限り、そのまま使う。画像名を変更する場合は、同じ変更内で Markdown の参照もすべて更新する。

## 検証チェックリスト

- `find docs/<article-slug> -maxdepth 2 -type f | sort` で、期待される README と画像が表示される。
- `rg` で、古いスペルミスのあるパスや移動前の画像パスへの参照が残っていないことを確認する。
- 記載したコマンドが、`package.json`、scripts、Makefile、または関連するプロジェクト設定と一致している。
- 記事内で説明したコマンド結果は、ローカルで検証済みであるか、スクリーンショット由来の例として明確に説明されている。
